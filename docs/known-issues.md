# Известные проблемы

Ошибки и ограничения текущей версии (по состоянию на коммит `b2eac36`).
Пункты, отмеченные «подтверждено», воспроизведены на коде; «возможно» —
следуют из чтения кода, но не проверены на живом API.

Когда проблема исправлена, удалите её отсюда (см. [Ведение документации](dev/docs-guide.md)).

## Высокий приоритет

### Cloudflare: теряется последняя тысяча доменов

**Подтверждено.** `ListService.cutChunks` при количестве доменов больше 1000
и кратном 1000 отбрасывает последний полный чанк и добавляет пустой:

| Доменов | Ожидаемые чанки | Фактические |
|---|---|---|
| 1500 | 1000, 500 | 1000, 500 |
| 2000 | 1000, 1000 | 1000, **0** |
| 3000 | 1000, 1000, 1000 | 1000, 1000, **0** |

Последняя тысяча доменов не попадает в Cloudflare, а запрос на создание пустого
списка может вернуть ошибку. Касается и блокировок, и перенаправлений (для
каждого IP отдельно).

**Обход:** нет надёжного; ситуация редкая (требуется точная кратность 1000).

### NextDNS: очистка удаляет ручные записи

**Подтверждено.** Если не заданы ни `BLOCK`, ни `REDIRECT`, скрипт удаляет **весь**
denylist и **все** rewrites профиля (`NextDnsDenyService.removeAll`,
`NextDnsRewriteService.removeAll`). Записи, созданные скриптом, ничем не
помечены, поэтому отличить их от ручных нельзя. Прежняя формулировка README
(«удаляются ранее сгенерированные данные») это не отражала.

**Обход:** не запускайте скрипт для NextDNS без источников, если в профиле есть
ручные записи. Для отключения синхронизации выключите workflow, а не очищайте
переменные.

## Разбор источников

### Табуляция между IP и доменом роняет скрипт

**Подтверждено.** Распознавание строк ищет пробел (`"0.0.0.0 "`,
`line.indexOf(" ")`). Строка `1.2.3.4<TAB>site.example` даёт
`StringIndexOutOfBoundsException` и аварийное завершение. Строка
`0.0.0.0<TAB>site.example` не распознаётся как блокировка, уходит в разбор
перенаправлений и падает так же.

**Обход:** использовать источники, где разделитель — пробел.

### Пробелы в списке ссылок

**Подтверждено.** `EnvParser.parse` делит строку по запятой без обрезки
пробелов: `https://a/hosts, https://b/hosts` → ссылка `" https://b/hosts"` →
`IllegalArgumentException: Illegal character in scheme name at index 0`.

**Обход:** перечислять ссылки без пробелов.

### Комментарии в строке, несколько доменов, служебные записи

**Подтверждено.** Для перенаправлений доменом считается весь остаток строки после IP:

- `1.2.3.4 site.example # comment` → домен `site.example # comment`;
- `1.2.3.4 a.example b.example` → домен `a.example b.example`;
- `255.255.255.255 broadcasthost`, `ff02::1 ip6-allnodes`, `fe80::1%lo0 localhost`
  трактуются как перенаправления.

Такие записи затем отвергаются API провайдера (в логе — ошибка запроса) или
создают бессмысленное правило.

### Не проверяется ответ при загрузке источника

**Подтверждено.** `ListLoader.fetchList` не смотрит на HTTP-код и не следует
редиректам (`HttpClient` по умолчанию — `Redirect.NEVER`). Страница 404 будет
разобрана как hosts-файл, ссылка с редиректом вернёт пустое тело без
предупреждения.

### Дубликаты после удаления `www.`

**Возможно.** `distinct()` выполняется до удаления префикса `www.`, поэтому
`0.0.0.0 www.a.example` и `0.0.0.0 a.example` дадут `a.example` дважды в списке
блокировок. Для Cloudflare это дубликат элемента в списке, для NextDNS —
повторный запрос на добавление. Как на это реагирует API, не проверялось.
Для перенаправлений дубликаты устраняются (`putIfAbsent`).

## Cloudflare

### Обновление не атомарно

Старые правила и списки удаляются до создания новых. При сбое посреди запуска
часть блокировок и перенаправлений будет отсутствовать до следующего успешного
запуска.

### Пустой ответ `GET /rules`

**Возможно.** Для списков ответ `result: null` обрабатывается
(`requireNonNullElse`), для правил — нет (`RuleService.obtainExistingRules`).
Если API вернёт `null` для аккаунта без правил, сценарий упадёт с
`NullPointerException`.

## NextDNS

### Удалённые из источника записи остаются

Это особенность стратегии, а не сбой: домены, пропавшие из источников, не
удаляются ни из denylist, ни из rewrites. Полностью пересинхронизировать
можно только через очистку (с учётом
[проблемы выше](#nextdns-очистка-удаляет-ручные-записи)).

### Неактивные записи denylist

**Возможно.** `dropExistingDenys` исключает только **активные** существующие
записи. Для домена, который уже есть в denylist, но выключен, будет отправлен
повторный `POST`; ответ API в этом случае не проверялся.

### Неверное число источников в логе

**Подтверждено, косметика.** `Obtain rewrite lists from N sources` выводит
количество источников `BLOCK`, а не `REDIRECT` (`NextDnsTaskRunner`).

## Для разработчиков

- `HttpRequestSender.sendRequest`: если `httpClient.send` бросает исключение,
  `semaphore.release()` не вызывается. Сейчас это не проявляется, потому что
  исключение всё равно завершает работу, но при добавлении повторов станет
  утечкой разрешений.
- Тестов нет; `System.exit` в глубине HTTP-слоя и `static final` переменные
  окружения мешают их написать.
